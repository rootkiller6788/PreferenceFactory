## 二、核心命题

**它不是简单生成 chosen/rejected。** 真正的问题是：

> Preference Evidence 怎么产生、验证、去噪和版本化？

## 五、建议数据结构

```
PreferenceRecord
├── prompt
├── candidates[]
├── ranking
├── judges[]
├── scores[]
├── agreement
├── confidence
├── rationale
└── provenance
```

`agreement` / `confidence` / `provenance` 三个字段是关键——它们让每条偏好数据都**自带可信度与来源**，而不是一个裸的 `chosen/rejected` 对。

## 六、最核心的是这条链

```
Generate
 ↓
Judge
 ↓
Cross-Judge Agreement
 ↓
Filter
 ↓
Preference Evidence
```

**而不是单个 LLM Judge。**

单裁判的问题：模型自身的偏好、位置偏差、长度偏差会直接固化进数据。多裁判 + 一致性检验 + 置信度过滤，才能把"某个模型的偏好"升级为"可辩护的偏好证据"。

## 七、阶段性落地计划

- **M0｜Record 骨架**：定义 PreferenceRecord schema，跑通 Prompt → Generate → 人工标注一次（非自动）。
- **M1｜Judge Pool**：实现 Human / LLM / Rule 三类裁判与 Cross-Judge Agreement 计算。
- **M2｜去噪与过滤**：实现 Confidence Score、Bias / Noise Check（位置偏差、长度偏差、自我偏好）与过滤。
- **M3｜版本化与发布**：偏好数据集版本管理、可复现导出与统计报告。

## 八、验收标准

能端到端完成「PreferenceFactory」，并在其「核心」（偏好数据生成 → Judge → 过滤）上给出可复现的量化结果：

- 每条偏好数据带 agreement / confidence，可量化裁判一致率
- 能给出偏差检测结果，并说明过滤掉了多少噪声样本

# 附录 A｜骨架、快速开始、CLI 契约、产物

## A.1 目录

```
L4-preferencefactory/
├── configs/default.json            所有口径与门槛（代码里不硬编码任何阈值）
├── data/prompts.jsonl              prompt 池快照（带可验证判据，首次 run 时生成）
├── src/preferencefactory/
│   ├── rng.py                      确定性随机（sha256 派生种子）+ canonical_json
│   ├── schema.py                   对象模型：Prompt / Candidate / JudgeSpec / Verdict / PreferenceRecord
│   ├── config.py                   配置加载 + 校验 + 两类摘要（protocol / version）
│   ├── prompts.py                  prompt 池 + 渲染 + **四条机械可判定判据**（含部分分）
│   ├── candidates.py               4 个候选族 × 题型能力加成 → Candidate
│   ├── judges.py                   三类裁判统一打分模型（偏差是注入参数，不是代码分支）
│   ├── agreement.py                逐对一致率 / Fleiss' κ / 置信度 / 聚合与降权聚合
│   ├── probes.py                   三套陷阱（换序 / 长度 / 自家族）+ 对照集
│   ├── filter.py                   四条过滤规则 + 漏斗 + 噪声账本
│   ├── dataset.py                  内容寻址版本 + 导出（剥掉隐藏真值）
│   ├── lineage.py                  血缘 DAG（加边时拒绝成环）
│   ├── pipeline.py                 编排 + 落盘 + load_result
│   ├── acceptance.py               验收清单 + 对抗用例（**本项目的质量闸门**）
│   ├── report.py                   markdown 报告
│   ├── visualize.py                自包含 HTML（零外部资源）
│   └── cli.py                      3 写 + 15 只读子命令
├── tests/                          CLI 契约 / JSON / 编码回归（见 A.5）
├── main.py                         入口（零安装：把 src/ 塞进 sys.path）
└── out/                            产物（见 A.4）
```

**形状：直线流水线（记录流）+ 每记录内的裁判扇出-收拢。** 被优化的对象是**没有的**
（`objectives_of()` 返回空元组）—— 一旦有了目标函数，「哪条偏好更好」就会混进一份
只该回答「这条证据有多可信」的报告里。扇出的是**裁判**，收拢点是**一致率**。

**四层对象链**：

```
Prompt（带可验证判据）  ×  Family（能力 + 长度倾向 + 题型加成）
        │  generate
        ▼
Candidate（criteria 可观测 / quality 隐藏真值 / pad_chars 与真值无关的长度）
        │  all_pairs（同 prompt 内，展示顺序随机）
        ▼
Pair  ──×  JudgeSpec ──▶  Verdict（带 factors / rationale / provenance）
        │  agreement_of + kappa_of + confidence_of
        ▼
PreferenceRecord（带 agreement / confidence / evidence / truth）
        │  filter_records（四条规则，逐条留证据）
        ▼
Preference Dataset（v1-<digest12>，导出时剥掉真值）
```

**三个「质量」必须分清**，混了就没法解释结果：

| 名字 | 谁能看见 | 口径 |
| --- | --- | --- |
| `criteria` | `rule` 裁判（机械可判） | 四条判据部分分的均值 |
| `polish` | 只有 `human` / `llm` | 无法被任何机械判据观测的残差 |
| `quality` | 隐藏真值 | `0.8·criteria + 0.2·polish` |

那 20% 的残差是**刻意留的**：没有它，`rule` 裁判就等于真值本身，「rule 同意才保留」
这条过滤规则会强得不像真的。留了盲区之后 `rule` 的定位才对 —— **最可信的锚点，不是神谕**
（实测它与真值一致 85.8%）。

## B.2 验收标准逐条核对

> **① 每条偏好数据带 agreement / confidence，可量化裁判一致率**

288 条记录**全部**带 `agreement` / `kappa` / `confidence` / `verdicts` / `provenance`，
缺失 0 条。一致率均值 **0.615**，κ 均值 **0.320**，置信度均值 **0.412**。

κ ≤ 一致率是代数必然（κ=(P̄−Pe)/(1−Pe)，而 Pe(1−P̄) ≥ 0），288 条全部满足。
κ 低不代表算错，它代表「扣掉乱猜也能撞上的部分之后，剩下的共识不多」。

裁判两两一致率（全表，`out/agreement.json` 亦有）：

| | `rule` | `human` | `llm-alpha` | `llm-beta` | `llm-gamma` |
| --- | --- | --- | --- | --- | --- |
| `rule` | — | 0.76 | 0.59 | 0.52 | 0.69 |
| `human` | 0.76 | — | 0.59 | 0.53 | 0.67 |
| `llm-alpha` | 0.59 | 0.59 | — | 0.72 | 0.56 |
| `llm-beta` | 0.52 | 0.53 | 0.72 | — | 0.51 |
| `llm-gamma` | 0.69 | 0.67 | 0.56 | 0.51 | — |

最一致的一对是 `llm-alpha`↔`llm-beta`（0.72），最不一致的是 `llm-beta`↔`llm-gamma`（0.51）
—— 而 `llm-beta` 是长度偏差最重（λ=0.40）的那个，`llm-gamma` 是自我偏好最重（σ=0.38）的那个。
**两个有偏方向不同的裁判，一致率最低**，这本身就是「一致率在起作用」的证据。

> **② 能给出偏差检测结果，并说明过滤掉了多少噪声样本**

**偏差检测（注入量 vs 检出率）**：

| 裁判 | 归属族 | β位置 | λ长度 | σ自我 | 检出位置 | 检出长度 | 检出自我 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `rule` | — | 0.00 | 0.00 | 0.00 | **0.000** | **0.000** | 不适用 |
| `human` | — | 0.00 | 0.00 | 0.00 | **0.000** | **0.000** | 不适用 |
| `llm-alpha` | plain | 0.30 | 0.28 | 0.22 | 0.792 | 0.347 | 0.339 |
| `llm-beta` | careful | 0.16 | 0.40 | 0.08 | 0.238 | 0.811 | 0.033 |
| `llm-gamma` | terse | 0.06 | 0.10 | 0.38 | 0.000 | 0.000 | 0.941 |

**三条轴的秩相关都是 0.918 / 0.918 / 1.000**（注入次序 vs 检出次序）：
位置 ρ=0.918、长度 ρ=0.918、自我 ρ=1.000。量纲不同（注入的是打分偏移量，检出的是踩中率），
能要求的只是一场**次序一致**。（位置与长度没到 1.000，是因为 `llm-gamma` 那一档注入量
最小（0.06 / 0.10），检出被压在 0 —— 它和两个 0.00 的锚点并列，秩上出现平局。）

**最关键的一条**：两个无偏裁判的三轴检出全部为 0 —— 检测器不冤枉好人。
（`human` 的噪声是 0.11，它在陷阱上**本来就会踩中 12.5%**；见坑 116。）

**噪声账本**：

| 项 | 数值 |
| --- | --- |
| 记录总数 | 288 |
| 其中噪声 | 69（**24.0%**） |
| 保留 | 180（剩噪声 3 条，**1.7%**） |
| 丢掉 | 108 |
| 丢掉的里真是噪声 | 66（精度 **61.1%**） |
| 噪声召回 | **95.7%** |
| **提升倍数** | **2.55×** |

**为什么必须看提升倍数**：精度的上限是 `噪声总数 / 丢掉数` = 69/108 = 0.639，越不过去。
所以「过滤掉了 N 条噪声」这句话本身没有信息 —— 随机丢 N 条也能丢到噪声，命中率就是
基础噪声率 24.0%。2.55× 才回答「这个过滤器到底有没有在挑」。

## B.3 三条偏差轴是怎么测出来的

| 轴 | 陷阱构造 | 统计量 | 为什么这个统计量是干净的 |
| --- | --- | --- | --- |
| position | 质量相当的一对（真值差 ≤ 0.10）换序判两次 | 两次都确定却点名了不同候选 → 记一次改口 | **噪声按 `(裁判, 候选)` 固定**，所以噪声不会造成改口；改口只可能来自位置加分 |
| length | 更长的那个其实更差（真值差 ∈ [0.08, 0.30]） | 点名更长的比例 − 同难度对照集上的失误率 | 减掉「他本来就有的失误率」之后，剩下的才是偏差 |
| self | 自家候选族产出的那个其实更差，且两条长度差 ≤ 8 | 点名自家的比例 − 同难度对照集上的失误率 | 长度配平 + 难度配平，两条轴不再纠缠 |

## B.4 设计期望 vs 实测（**两条被推翻**）

| 设计期望 | 实测 | 结论 |
| --- | --- | --- |
| `confidence_correlates_with_true_margin` | ρ(confidence, 真值差) = **0.767** | 成立 |
| `filter_precision_above = 0.60` | 精度 **0.611** | 成立（勉强） |
| `rule_judge_agrees_with_truth` | 与真值一致 **85.8%**（236/275） | 成立但**不到 100%** —— 它看不见那 20% 的残差 |
| `weighted_verdict_beats_majority` | 多数票 219/275 → 降权票 **241/275** | 成立（+8%） |
| `weighted_verdict_beats_majority_in_every_kind` | arith 49→54｜reverse 59→64｜sort 59→65｜upper 52→58 | 成立，四个题型全改善 |
| **`retention_spread_under = 0.10`** | 各题型保留率差 **18.1%**（arith 51.4% / upper 62.5% / reverse 66.7% / sort 69.4%） | **被推翻**：过滤器对题型有系统性偏好 |
| **`tie_verdicts_track_true_ties`** | 裁判平局 **15.6%** vs 真值平局 **4.5%**（3.5×） | **被推翻**：裁判的 `tie` 大多是「它判不出来」，不是「真的一样好」 |

两条被推翻的期望，各自指出一个真问题：

**（一）过滤器对题型有系统性偏好。** 算术题的保留率 51.4%，排序题 69.4%。
原因不是过滤器偏袒，而是**算术题的判据分更分散**（乘加结果错一位就是大误差），
于是同一个 `min_agreement` 门槛在算术上拦下的更多。要让四个题型均衡，
门槛应当**按题型的真值差分布标定**，而不是全局一个数。这是下一步该做的事。

**（二）裁判的 `tie` 不等于真值的 `tie`。** 裁判说平局 15.6%，而真值平局只有 4.5%。
也就是说裁判的 `tie` 大部分是**「我判不出来」**（真值差小于它的噪声/偏差尺度），
而不是「两个候选真的一样好」。这恰好解释了置信度为什么有效：真值差小的记录
→ 裁判分歧大 / 频繁判平局 → 一致率与果断度双低 → 置信度低 → 被过滤。
**过滤器不是靠「猜对了」起作用的，是靠「知道自己什么时候不该下结论」。**

## B.5 过滤漏斗

| 规则 | 首因归因 | 独立失败数 |
| --- | --- | --- |
| `agreement`（一致率 ≥ 0.35） | 64 | 64 |
| `confidence`（置信度 ≥ 0.20） | 36 | 100 |
| `rule_agreement`（无偏锚点不得反对） | 8 | 27 |
| `untainted_support`（至少一个无染裁判支持） | 0 | 45 |
| **保留** | **180** | — |

两种口径都要：首因归因回答「主要被谁卡住」，独立失败数回答「谁最有杀伤力」——
独立失败数合计 236 > 丢掉数 108，说明**大量记录同时踩了不止一条**：其中 36 条只踩一条、
31 条踩两条、26 条踩三条、15 条踩四条，**共 72 条被两条以上卡住**。首因归因会把它们
全记在第一条名下，所以单看首因列会低估 `confidence` 的杀伤力（它首因只有 36，独立却有 100）。

门槛是**扫过一轮**定的（288 条上跑 3×3 网格）：0.60/0.30 只留 16%，0.35/0.20 留 62.5%
且噪声率 24.0% → 1.7%。0.35 的含义是「至少 3/5 干净多数（3-2 → 0.40）」。

## B.6 可复现性边界

- 版本是**内容寻址**的：digest 吃导出形态（剥掉真值之后）的逐条摘要，
  所以「版本号相同 ⇒ 数据集逐位相同」。
- 唯一不可复现的字段是 `created_at`，它不进 digest。两次 `run` 得到同一个 `v1-f503b728a71e`。
- 噪声按 `(裁判, 候选)` 确定性派生；**不用** `random.gauss` / `random.shuffle`（实现细节
  在不同 CPython 小版本里改过），只用 `random.random()`（MT19937，有跨版本稳定性保证）。
- **已知的缝**：`rule` 裁判只能看到 `criteria`，真值里还有 20% 它看不见。
  所以「rule 同意才保留」会漏掉一些好记录 —— 这是精度只有 61.1% 而召回 95.7% 的原因之一。
  真实场景里验证器也从来不是神谕，这个缝是刻意留的，不是没修。

# 附录 C｜坑（109–125）

编号接着 `L3-finetunefactory` 的 108。

### 109. 真值退化成二值：576 个候选里 500 个满分，76% 的记录「两个候选一样好」

**症状**：第一次跑通之后，`truth_tie_rate = 0.757`，`quality` 只有 4 个取值
（`0.25 / 0.5 / 0.75 / 1.0`），其中 500/576 是满分。

**原因**：判据难度定在 0.34–0.58，而候选族的能力在 0.72–0.90 —— **几乎所有人都过**。

**为什么这很危险**：过滤器的表现会变得**虚假地好**。基础噪声率 78%，只要把平局全丢掉，
噪声率立刻掉到 5%，精度也能到 0.87。但那是**把「两个候选一样好」当成噪声**捡的便宜，
不是过滤器在识别偏差。这一版的漂亮数字全是假的。

**修法**：判据难度推到候选能力**之上**（`exact` 0.90 / `tidy` 0.80 / `clean` 0.70 /
`punct` 0.62），于是「完全答对」变成少数。真值平局率从 76% 降到 4.5%。

### 110. 二值判据 + 没有部分分 → 真值仍然是 5 级阶梯

**症状**：难度调高之后好一些，但 `quality` 还是只有 5 个取值，46% 的候选拿满分，
真值仍然挤在顶端。

**原因**：`quality = 通过的判据数 / 判据总数` 是**阶梯函数**。判据只有 4 条，
阶梯就只有 5 级。

**修法**：给 `exact` 判据加**部分分** —— 算术题按 `|答案 − 正确值| / 归一化尺度` 扣分，
字符串题按归一化汉明距离扣分。`rule` 裁判的无偏性一点没丢（部分分仍然完全机械），
丢的只是粗糙度。真值这才连续。

### 111. 部分分与扰动幅度不挂钩 → 部分分还原不出能力差异

**症状**：加了部分分之后，「错一点」和「错很远」拿到同一个分。真值还是分级的。

**原因**：`_perturb` 的扰动幅度是**固定**的（算术题 ±1..6、字符串题错 1–2 个字符），
与 `latent` 离及格线有多远（`err`）无关。

**修法**：`_perturb(..., err)`，错误幅度 ∝ `err`，并且**扰动与打分用同一个归一化尺度**
（`_arith_scale`）。这一对必须成对改 —— 只改一边，部分分就还原不出距离。

### 112. 能力最强的族全面碾压 → 自我偏好轴的样本数为 0

**症状**：`llm-gamma` 的 self 探针 `n = 0`，检测器直接哑掉；`build_self_units`
返回空集。而 `llm-alpha` / `llm-beta` 各有 33 / 22 条。

**原因**：`careful` 族的 `skill = 0.90`，别的族 0.72 —— 「自家候选**更差**」的样本
根本不存在。**自我偏好这条轴需要一个「自家更差」的场景才测得到。**

**修法**：给每个族加 `kind_bonus`，让四个族各擅长一个题型、各有短板：
`terse` 强在算术（+0.10）、`plain` 强在大写（+0.09）、`verbose` 强在倒写（+0.11）、
`careful` 强在排序（+0.13）。于是每个族在某些题型上会输，self 陷阱就有了样本。
这同时也更真实：**不同模型本来就擅长不同任务。**

### 113. self 轴校准失败（ρ=0.50）：注入 0.38 的裁判测出来比注入 0.22 的低

**症状**：`校准[self]：注入次序 == 检出次序 | Spearman ρ=0.500`。注入
`gamma=0.38 > alpha=0.22`，检出 `alpha=0.923 > gamma=0.792` —— **次序反了**。

**两个原因叠加**：

1. **陷阱难度没配平**。每个裁判的自家族不同，各自陷阱集里的「真值差」分布也不同：
   一个裁判的陷阱是「差 0.30 明显更差」，另一个的是「差 0.05 险胜」。难度不一样，
   检出率就不可比。
2. **长度偏差在 self 陷阱里替自家族说话**。`verbose` 族的候选比别人长 ~10 个字符
   （中位 25 vs 12–17），于是归属 `verbose` 的裁判在自家族陷阱里同时吃到长度加分。

**修法**（三条一起上）：

- `trap_gap_lo/hi = [0.08, 0.30]`：所有裁判的陷阱真值差落在同一段。
- `self_length_band = 8`：陷阱对的两条候选长度必须接近。
- **三个 llm 裁判归到 verbosity 接近的族**（`plain` 1.00 / `careful` 1.10 / `terse` 0.85），
  `verbose`（1.95）**不给任何裁判**，它只负责提供长度方差。

改完 ρ = **1.000**。

### 114. `human` 被误判为有长度偏差（0.125 > 容差 0.12）

**症状**：`无偏裁判不被指控` 这条验收项红了：`human/length=0.125(n=48)`。
一个**构造上无偏**的裁判被测出了偏差。

**原因**：`human` 的噪声是 0.11，而长度陷阱的真值差只有 0.08–0.30。噪声大的裁判
在陷阱上**本来就会踩中** —— 那不是偏差，那是它本来就有的失误率。检出率直接拿踩中率
当偏差量，等于把「不准」和「有偏」混为一谈。

**修法**：给每个陷阱集配一个**同难度的对照集**（长度轴上：更长的那个**确实更好**），
把裁判在对照集上的失误率写进 `ProbeResult.baseline`：

```
detected = 踩中率 − 自身失误率
```

改完 `human` 的长度检出掉到 **0.000**，而 λ=0.40 的裁判仍有 0.811。
**这一条是「不冤枉好人」的关键**：检测器必须能区分「他有偏」和「他不行」。

### 115. 渲染 ↔ 判据往返断了 4/288：扰动可能是个空操作

**症状**：`渲染 ↔ 判据往返一致 | 288 个候选里 4 个对不上`。

**原因**：两处扰动会**什么都没改**：

- `reverse`：交换的两个位置上的字符**相同**（`cascade` 反转后有重复字母）→ 文本不变。
- `upper`：随机挑的索引落在**空格**上（`isalpha()` 为假）→ 跳过，文本不变。

于是「标记为违反 `exact`」的候选，重新解析回来仍然是满分 —— 生成时写进
`checks_passed` 的标签和判据的重新判定不一致。**`rule` 裁判读的必须是候选真实写的东西**，
这个不一致会让所有「rule 与真值的对照」失去意义。

**修法**：`reverse` 只从「内容不同」的位置对里挑；`upper` 只从**大写字母**的索引里挑；
两者都加「实在改不动就加个 `x`」的兜底。

### 116. 长度与真值相关 −0.361：违反判据直接加字符

**症状**：`长度与真值弱相关 | corr(长度, 真值)=-0.361（|·| <= 0.30）`。

**原因**：违反判据的代价是**加字符** —— 犹豫标记 `〔?〕` 加 3 个、多余空格加 2 个。
于是「答得差」和「写得长」绑在一起，长度偏差和「长答案确实更差」彻底纠缠，
长度轴的检出率就没有干净的解释了。

**修法**：**长度预算制**。`verbosity` 先定一个总填充预算，违反判据的代价
（犹豫标记 / 多余空格 / 句号）**先从预算里扣**，剩下的才用来铺引导语。
长度于是主要由 `verbosity` 决定，与真值无关。改完 corr = **−0.206**。

### 117. 换序探针的样本从 96 掉到 1–19

**症状**：`match_tolerance = 0.02` 时，换序探针只找到 16/288 对可用样本，
`rule` 的位置轴 `n = 1` —— 检出率是 0.000 还是 1.000 都没有意义。

**原因**：0.02 这个容差是**真值还是分级的时候**定的，那时有大量「完全一样好」的对。
真值改成连续的之后，|Δq| ≤ 0.02 只剩 16 对。

**修法**：放宽到 0.10（~75 对）。放宽**不会引入偏差** —— 真值差越大越不容易「改口」，
只会稀释检出率，次序仍然可比。这是一次「参数的含义随上游改动而失效」的典型：
调参时对，改完上游就成了错的。

### 118. 产物不全时，验收清单静默少跑两项

**症状**：内存里跑是 17 项，从产物读是 **15 项**，而且**没有提示**。

**原因**：`渲染↔判据往返` 与 `长度与真值弱相关` 都写成 `if result.candidates:`，
而 `load_result` 当时不恢复 prompts / candidates。于是这两项被**静默跳过**。

**为什么这比失败更危险**：失败会红，跳过是绿的。一个「13/13 通过」的报告会让人
以为全都核对过了。**验收清单的项数必须是固定的** —— 少一项就意味着少了一道闸门。

**修法**：把 `prompts.jsonl` / `candidates.jsonl` 也写进产物，`load_result` 恢复它们。
产物自包含顺带还有个好处：拷给别人就能复算。

### 119. `summary --json` 被 argparse 拒绝，报错却出现在 JSON 解析里

**症状**：`summary: json.decoder.JSONDecodeError: Expecting value: line 2 column 1 (char 1)`。

**原因**：`summary` 子命令**忘了挂 `--json`**。argparse 报 `unrecognized arguments`、
退出码 2、stdout 为空；外层脚本读到空字符串去 `json.load`，于是报错位置离真正的原因
隔了两层。

**修法**：给 `summary` 补上 `--json`。更重要的教训是**要有一张「哪些命令支持 `--json`」
的清单并逐个跑一遍** —— 这个 bug 是靠一条循环里 14 个命令全部 `json.load` 才发现的。

### 120. `--json` 只「追加」一段 JSON，于是没法 pipe

**症状**：`python main.py zoo --json | jq` 报错。

**原因**：`--json` 的实现是「照常 print 说明文字，最后再 print 一段 JSON」。
于是 stdout 里是「文字 + JSON」，任何下游解析器都会挂。

**修法**：`_quiet_prose` 上下文管理器在 `--json` 时把 `sys.stdout` 换成 `StringIO`
（吞掉命令自己的 `print`），`_emit_json` 直接写**真正的** `sys.stdout`
（模块导入时就存下来的 `_REAL_STDOUT`）。这样命令代码一行都不用改。

### 121. 我自己手误建了一整棵目录树，而这个工作区没有 git 兜底

**症状**：写文件时把路径敲成 `D:/Opcode my-project/...`（少了个 `n`、多了个空格），
于是 `D:/Opcode my-project/factory-everything/L4-preferencefactory/src/preferencefactory/`
被建了出来，文件写在了那里。

**为什么危险**：当时这个工作区 `git status` 报 `fatal: not a git repository`，
**当时没有版本控制兜底**，也没有任何东西会提醒「你刚建了一个不该存在的目录」。
（2026-10-07 注：工作区根**现在已是** git 仓库，本项目也有一批文件在版本控制里，
但**当前改动尚未提交** ⇒ 结论不变。）
如果那个文件之后再没被读到，这个错误会一直躺着。

**处理**：`find` 确认那棵树里只有我自己刚写的那一个文件 → `cp` 到正确位置 →
逐级 `rmdir`（用 `rmdir` 而不是 `rm -rf`：**非空就删不掉**，这个性质本身就是一道保险）。

### 122. schema 加字段之后，对抗用例直接崩

**症状**：`TypeError: Candidate.__init__() missing 2 required positional arguments:
'criteria' and 'polish'`。

**原因**：验收/对抗里为了造极端样本**手搓了 `Candidate`**。给 schema 加字段之后，
这些手搓点全部失效。

**教训**：手搓对象在 schema 演进时是脆的。**能复用生成器就复用生成器** ——
`adversarial` 里的合成池本来就是调 `generate_for_pool` 造出来的，只有那个「破坏判据」
的样本是手搓的。手搓的收益（少跑一次渲染）远小于代价（schema 一动就崩）。

### 123. `manifest` 是 dataclass，不是 dict

**症状**：`TypeError: 'DatasetManifest' object is not subscriptable`。

**原因**：诊断脚本里写了 `res.manifest["stats"]["truth_tie_rate"]`，
而 `manifest` 是 `@dataclass(frozen=True)`，要 `.stats`。

**教训**：这类错在**一次性脚本**里特别常见 —— 正式代码里类型标注会提示，
但排查问题时随手写的脚本没有。它本身不是代码 bug，但它浪费的那几分钟
应该记下来：**诊断脚本也要当代码写。**

### 124. 门槛扫描的结论「`confidence_scale` 不起作用」是扫描脚本的错

**症状**：3×3×2 的门槛网格里，`confidence_scale` 取 0.35 和 0.50 得到**完全一样**的结果。

**原因**：`confidence` 是在**判定阶段**算好、写进记录里的；扫描脚本只重跑了
`filter_records`（过滤阶段）。所以改 `judging.confidence_scale` 当然不影响结果。

**教训**：**「改了参数没反应」的第一嫌疑是测试装置，不是被测代码。**
在得出「这个参数没用」的结论之前，先确认它有没有真的被读到。

### 125. 精度的上限是基础噪声率决定的，只看精度会得出错误结论

**症状**：第一版门槛（0.60/0.30）下精度 0.434，看起来「过滤器很一般」。
但它丢掉了 84% 的记录，而基础噪声率只有 29.5% —— 精度的**理论上限**就是
`29.5% / 84% = 0.35`，实测 0.434 已经**超过**上限了（因为噪声总数/丢掉数的比在变）。

**原因**：精度 = `丢掉的里真是噪声 / 丢掉的总数`。丢得越多，分子最多是全部噪声，
分母却线性增长，所以精度**必然被基础噪声率钉死**。

**修法**：报告里改用**提升倍数** `precision / 基础噪声率`。它回答的是
「比随机丢好多少」，量纲干净、不受门槛松紧影响（实测 2.55×）。
`NoiseReport.lift` 现在是验收项之一，`noise` 命令也把它放在最后一行。
